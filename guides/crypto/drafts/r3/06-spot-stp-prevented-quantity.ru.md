# Самосделки и предотвращённые исполнения

**DRAFT_HOLD.** Учебный материал; не разрешение на запросы или сделки.

## 1. Что делает STP
Self-trade prevention (STP) — механизм, позволяющий предотвратить встречное исполнение собственных заявок. В Binance Spot область сравнения включает один аккаунт либо разные аккаунты, объединённые одинаковым установленным tradeGroupId [S1]. Значение -1 означает отсутствие установленной группы, а не принадлежность всех таких аккаунтов к общей группе. Это не доказательство отсутствия самосделок при работе нескольких систем.

Проверяйте допустимые режимы и режим по умолчанию для конкретного символа: allowedSelfTradePreventionModes и defaultSelfTradePreventionMode [S1]. Не переносите параметры одного инструмента на другой. Статья не рекомендует выбирать режим, отключать STP или проверять механизм реальными встречными заявками.

## 2. Режимы и область предотвращённого количества

| Режим | Смысл в пределах документации [S1] |
|---|---|
| NONE | STP не предотвращает совпадение |
| EXPIRE_TAKER | Прекращается оставшееся количество заявки taker |
| EXPIRE_MAKER | Прекращается оставшееся количество потенциальной заявки maker |
| EXPIRE_BOTH | Прекращаются оставшиеся количества обеих заявок |
| DECREMENT | У обеих заявок учитывается предотвращённое количество совпадения; меньшая исчерпывает остаток |
| TRANSFER | Особый режим; для разных аккаунтов одной группы возможен перенос активов |

В общем случае поведение зависит от режима taker. В приведённой документации TRANSFER требует соответствующего режима у обеих заявок; если его указал только taker, применяется DECREMENT. Фактически применённый режим может отличаться от указанного у конкретной заявки. Поля effectiveSelfTradePreventionMode и eV при наличии помогают различить эти случаи [S1, S2]. Отсутствие такого поля не означает NONE.

Не делайте вывод о неизменности балансов только по отсутствию сделки: для TRANSFER документация предусматривает перенос предотвращённого количества и его номинала между аккаунтами одной группы. Даже в обычном режиме изменение заблокированных средств требует отдельной сверки.

## 3. Три количества вместо одного остатка
Для открытой заявки с количеством в базовом активе документация [S1] связывает исходное, исполненное и предотвращённое количества.

Учебный пример без TRANSFER: исходное количество 5, реально исполнено 1.2, предотвращено 0.8. Доступное для дальнейшего исполнения количество равно 5 - 1.2 - 0.8 = 3.0. Исполненным остаётся 1.2, а не 2.0. Предотвращённое количество не является fill.

Если очередное событие содержит накопленное предотвращённое количество A = 1.1 и последнее B = 0.3, при подтверждённой последовательности оно совместимо с предыдущим A = 0.8. Нельзя прибавлять к предыдущему A сразу оба значения. Это синтетический пример, не обещание порядка доставки событий.

Формула остатка применяется к открытой заявке в указанном контексте. После прекращения заявки не объявляйте арифметический остаток доступным для исполнения. Сверьте статус и историю.

## 4. Как различать записи

| Наблюдение | Предлагаемая учебная проверка |
|---|---|
| executionReport с типом TRADE_PREVENTION | Отделить предотвращённое событие от торгового исполнения |
| Поля A и B | Различить накопленное количество и количество последнего события |
| Поля l и z | Отдельно сверить последнее и накопленное исполнение |
| Статус EXPIRED_IN_MATCH | Не считать все предыдущие исполнения равными нулю |
| Повтор записи или конфликт накопленных значений | HOLD до установления идентичности и согласованной истории |
| TRANSFER или неизвестный режим | HOLD для упрощённой модели; отдельная сверка движений активов |

Предлагаемый контроль: связывать записи с аккаунтом, символом, идентификатором заявки и доступными идентификаторами событий. Не смешивать preventedMatchId с tradeId; один предотвращённый матч может затрагивать обе заявки. В REST-справочнике [S3] для поиска предотвращённых матчей указан GET /api/v3/myPreventedMatches и предусмотрены сочетания symbol с preventedMatchId либо orderId. При этом FAQ [S1] в том же снимке использует другой путь. Это расхождение документации, а не подтверждение работоспособности обоих маршрутов. Перед реализацией нужно отдельно сверить актуальный контракт; запросов к аккаунту здесь не было.

## 5. Сверка двух сторон предотвращённого совпадения

Один preventedMatchId не означает одну заявку. Для сверки нужно установить связь с конкретным символом, аккаунтом и идентификатором каждой заявки, а также роль maker или taker. Для разных аккаунтов отдельно подтверждается установленная общая группа. Значение -1 у обоих аккаунтов не подтверждает принадлежность к одной группе.

Учебный пример: у taker исходное количество 5, исполнено 1.2, ранее предотвращено 0.8; остаток 3. У maker исходное количество 2, исполнено 0, предотвращено 0; остаток 2. При заданном совпадении в режиме DECREMENT предотвращается 2 на каждой стороне. После него у taker накопленное предотвращённое количество 2.8 и доступный остаток 1; у maker накопленное предотвращённое количество 2 и заявка завершена. Исполненные количества остаются 1.2 и 0.

| Условие учебной сверки | Ожидаемый результат |
|---|---|
| DECREMENT, обе стороны связаны с одним совпадением | Сверить одинаковый прирост предотвращённого количества |
| EXPIRE_TAKER | Сверить прекращение остатка taker, не приписывать предотвращённое количество maker |
| EXPIRE_MAKER | Сверить прекращение остатка maker, не приписывать предотвращённое количество taker |
| EXPIRE_BOTH | Сверить прекращение обоих остатков, которые могут быть разными |
| Нет подтверждения одной из сторон | HOLD |
| Режим TRANSFER применяется к совпадению | HOLD упрощённой модели; отдельная сверка движения активов |

Наблюдение неизменившейся стороны в этих упражнениях задано отдельно. Это не утверждение, что биржа обязана отправлять специальное событие о неизменившейся заявке. Нужны подтверждённые последовательность, принадлежность и полнота записей.

## 6. Почему отдельные корректные записи не доказывают согласованность пары

В том же исходном примере taker сообщает прирост предотвращённого количества 0.3, а maker — 2. Если оценивать каждую заявку отдельно, арифметика может быть непротиворечивой. Но при установленном общем совпадении DECREMENT такие приращения несовместимы. Модель R2 возвращает HOLD и не выдаёт согласованную проекцию.

Если taker указал TRANSFER, а maker другой режим, документация [S1] описывает применение DECREMENT. Если обе заявки указали TRANSFER, учебная модель R2 останавливается даже при одном аккаунте: это ограничение модели, а не запрет режима биржей. PAPER_PAIR_RECONCILED_SUBSET означает только согласованность заданных наблюдений количества. Это не доказательство полного исполнения, движения активов, комиссий или состояния заблокированных средств.

## 7. Граница применимости
HOLD — учебное локальное состояние неопределённости, не биржевой статус. Модель не доказывает доставку событий, полноту истории, разрешение повторной заявки, корректность реального учёта комиссий или движений между аккаунтами. Все количества условные; материал не содержит обещаний прибыли и не разрешает сделки.
